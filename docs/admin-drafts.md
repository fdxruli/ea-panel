# Admin Draft Infrastructure

The Admin Draft Store is a client-side recovery mechanism for unconfirmed work. It is intentionally independent from `CacheAdmin`.

## Layers

- Remote data: Supabase / `CacheAdmin`
- UI state: React state, hooks and contexts
- Work drafts: `AdminDraftContext` / `useAdminDraft` -> Dexie -> IndexedDB

No workflow is integrated in this phase. PHASE 2A establishes identity and ownership only; CreateOrder and EditOrderModal remain unchanged.

## Draft model

A draft contains:

- `id`: unique physical draft identity; multiple drafts may coexist.
- `version`: storage schema version (`1` currently).
- `ownerKey`: logical administrative owner, derived from the authenticated `session.user.id`.
- `workflow`: workflow/screen identifier.
- `entityType`: optional logical entity type.
- `entityId`: optional logical entity identifier; it is paired with `entityType`.
- `createdAt`: creation timestamp in milliseconds.
- `updatedAt`: last update timestamp in milliseconds.
- `expiresAt`: absolute expiration timestamp.
- `payload`: serializable work state only.
- `metadata`: minimal serializable metadata.

The physical `id` remains independent from the logical context. The logical context is `ownerKey + workflow + entityType + entityId` and is used for deterministic lookup; it is not encoded into the physical UUID.

`entityType` and `entityId` are both `null` for workflows without an entity. When an entity is present, both values are required. The infrastructure is prepared for future contexts such as `edit-order + order + order.id` without integrating those workflows in PHASE 2A.

Temporal timestamps are generated by the storage layer. Fase 1 intentionally does not enforce a separate `createdAt <= updatedAt <= expiresAt` invariant on arbitrary stored records; normal create/update operations produce coherent timestamps, while malformed records are rejected by the existing schema validation path.

## Ownership and authentication lifecycle

`ownerKey` comes only from the existing authentication context's canonical Supabase Auth user ID (`session.user.id`). Authentication logic is not duplicated in the draft layer.

The Admin Draft Provider resolves the owner only when the existing `AdminAuthContext` reports `ADMIN`. Therefore:

- `RESOLVING` -> `ownerKey = null`
- `UNAUTHENTICATED` -> `ownerKey = null`
- `CLIENT` -> `ownerKey = null`
- `ERROR` -> `ownerKey = null`
- `ADMIN` -> `ownerKey = session.user.id`

Without an owner, draft recovery/listing returns no drafts and draft creation is rejected with `ADMIN_DRAFT_OWNER_REQUIRED`. Pending debounced savers are cancelled whenever the owner changes, including logout and a later login as a different administrator. Existing drafts are not deleted during logout or owner changes.

All context-level reads, writes and deletes are owner-scoped. A draft belonging to another owner is treated as absent by the Admin Draft Context.

## Logical lookup

`findDraft()` matches the complete logical context:

- `ownerKey`
- `workflow`
- `entityType`
- `entityId`

The lookup uses the existing `workflow` Dexie index and then filters the remaining logical fields. Matching drafts are ordered by `updatedAt` descending, making the result deterministic without introducing a physical uniqueness constraint or locking system.

Owner and entity isolation are logical storage guarantees only. They do not provide authorization.

## TTL

The default TTL is 7 days (`DEFAULT_DRAFT_TTL_MS`). TTL is **absolute, not sliding, by default**:

- `createDraft()` sets `expiresAt = now + ttlMs`.
- `updateDraft()` without `ttlMs` preserves the existing `expiresAt`.
- `updateDraft()` with `ttlMs` explicitly replaces expiration with `now + ttlMs`.

Callers may provide a positive `ttlMs` at creation and update time. The value is deliberately centralized and named rather than embedded as a magic number.

Expired drafts are never returned as valid drafts. Reads/lists can opportunistically remove expired or malformed records, and `clearExpiredDrafts()` provides explicit cleanup.

## Versioning

`ADMIN_DRAFT_SCHEMA_VERSION` remains `1` in PHASE 2A. Owner/entity properties are additional object fields, not new Dexie indexes, so the existing object-store schema remains compatible and no migration registry is introduced.

The existing Dexie indexes remain `id`, `workflow`, `updatedAt`, `expiresAt` and `version`. The Phase 2A lookup intentionally uses the existing `workflow` index followed by exact logical-context filtering. A future change that requires indexed owner/entity queries can be evaluated separately before changing schema version.

Every read validates the stored schema version. An incompatible version is rejected and removed safely rather than being restored into UI state.

## Serialization contract

Payloads and metadata must be composed of plain objects, arrays, strings, booleans, finite numbers and `null`. Functions, Promises, React elements/references, AbortControllers, symbols, bigint values, `undefined`, non-finite numbers, Date, RegExp, Map, Set, circular references and other class instances are rejected.

Authentication tokens, credentials and secrets must never be placed in a draft payload.

## Security boundary

`ownerKey` is a logical isolation key for local IndexedDB data. It is **not**:

- authorization;
- an authentication mechanism;
- a security boundary;
- protection against DevTools or local IndexedDB manipulation;
- cryptographic integrity protection.

IndexedDB is client-controlled storage. A local draft must never be trusted to bypass current Supabase authorization or permissions. Remote writes remain authoritative.

## Persistence API

`src/lib/adminDraftStorage.js` provides:

- `createDraft`
- `getDraft`
- `updateDraft`
- `deleteDraft`
- `listDrafts`
- `findDraft`
- `hasDraft`
- `clearExpiredDrafts`
- `flushDraft`
- `createDebouncedDraftSaver`

`useAdminDraft()` exposes the same primitives plus workflow-friendly `load`, `exists`, `update`, `remove`, `flush` and `scheduleSave` helpers.

## Error isolation

IndexedDB availability is checked before opening the database. Storage errors are surfaced to callers so future workflow integrations can choose their own non-blocking fallback policy; the storage layer does not introduce an in-memory `Map` fallback. A draft is considered persisted only after IndexedDB confirms the write.

The test suite covers storage-unavailable behavior and a representative IndexedDB write failure (duplicate primary key). Low-level read-failure and quota-exhaustion simulation are intentionally not mocked through private Dexie internals in Fase 1; callers receive the underlying storage error when those conditions occur.

A future workflow integration must treat draft persistence as best-effort recovery, never as the source of truth for confirmed application data.

## Flush and debounce

`createDebouncedDraftSaver()` provides `schedule`, `flush` and `cancel`. The default delay is 500 ms. `flushDraft()` provides an explicit immediate persistence primitive for future `pagehide`/`visibilitychange` integration. Those browser lifecycle listeners are intentionally not installed in this phase.

The test suite verifies last-write-wins scheduling, debounce timing, cancellation, immediate flush, timer cancellation after flush and swallowed asynchronous save failures.

## React resource cleanup

`AdminDraftProvider` owns one debounced saver per draft ID. On provider unmount, all pending savers are cancelled and the saver map is cleared. Owner changes also cancel all pending savers so a scheduled write from one administrator cannot continue under another administrator's context.

## Cleanup

Cleanup is explicit and safe. Invalid or expired records encountered during reads/lists are removed, while `clearExpiredDrafts()` performs bulk cleanup. Cleanup is not wired into any existing Admin workflow in this phase.
